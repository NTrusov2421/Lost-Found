# ADR-001: Архитектурный стиль приложения

## Контекст

Проект — небольшой сайт на PHP без фреймворка. Существующий интерфейс состоит из серверных страниц и HTML-форм: каталог и поиск объявлений, регистрация и вход, создание и редактирование объявлений, профиль пользователя и панель администратора. Отдельный REST API в предоставленных материалах не подтверждён. Команда небольшая, поэтому дополнительная инфраструктура и сложный процесс развёртывания должны быть минимальными.

## Решение

Использовать **модульный монолит на PHP с серверной генерацией HTML**. Внутри приложения разделить ответственность на простые части:

- контроллеры — принимают HTTP-запросы и выбирают сценарий;
- сервисы — реализуют правила публикации, редактирования, истечения объявлений, сброса пароля и обработки жалоб;
- модели/слой доступа к данным — выполняют запросы к реляционной БД через подготовленные выражения;
- PHP-шаблоны — формируют страницы и повторно используемые элементы интерфейса;
- `storage/uploads` — хранит вложения, `storage/cache` — существующий JSON-кэш.

Вынести бизнес-логику в отдельный backend-сервис, строить микросервисы или вводить отдельный REST API на текущем этапе не требуется. Конкретный движок СУБД в этом ADR не фиксируется: его необходимо сверить с конфигурацией реально работающего проекта.

## Последствия

### Положительные

- Архитектура соответствует текущему PHP-сайту и не требует переписывать интерфейс на SPA.
- Один процесс развёртывания и меньше инфраструктурных расходов.
- Легче объяснить, отладить и тестировать в условиях небольшой команды.
- Разделение контроллеров, сервисов, доступа к данным и шаблонов упрощает изменение правил без дублирования логики.

### Отрицательные (ограничения)

- Все модули используют общий процесс и релиз; независимое масштабирование отдельных частей не предусмотрено.
- Без дисциплины границы модулей могут размываться, а файлы PHP снова начнут объединять логику и представление.
- Серверная генерация HTML подходит текущему проекту, но при появлении внешних клиентов может потребоваться отдельный API.

### Меры сопровождения

1. Не размещать SQL-запросы и бизнес-правила непосредственно в шаблонах.
2. Проверять права на сервере, а не полагаться на скрытие кнопок в интерфейсе.
3. Использовать подготовленные SQL-запросы и серверную валидацию входных данных.
4. Хранить загруженные файлы и JSON-кэш вне логики шаблонов; не допускать исполнения пользовательских файлов.
5. Добавлять API или отдельные сервисы только при появлении подтверждённой потребности.

## Рассмотренные альтернативы

- **Монолит без внутреннего разделения.** Проще изначально, но поддерживать и тестировать становится сложнее по мере роста числа сценариев.
- **Микросервисная архитектура.** Не выбрана: добавляет сетевые взаимодействия, независимые развёртывания и требования к эксплуатации, не оправданные размером проекта.
- **Отдельный REST API и SPA-клиент.** Не выбраны: текущий интерфейс уже построен на серверных страницах и отдельный API не подтверждён требованиями.
